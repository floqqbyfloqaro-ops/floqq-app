# FLOQQ Roadmap

_Snapshot of the live roadmap doc — read it there for the latest version and to comment: https://claude.ai/code/artifact/fdbee698-9930-40be-8d0b-25376a8ff3a2_

## Current status

FLOQQ is an MVP that matches airport-arrival passengers into shared taxi groups. Built so far:

- Passenger request intake, FlightAware flight lookup, and geocoding
- A 4-layer automated matching engine (Google Routes + a Supabase Edge Function) with a scheduled job that creates groups and re-scores them as flight times change
- Group confirmation flow, plus an admin dashboard (AdminScreen, GroupDetailScreen) for manual oversight
- FLOQQ service fee payment: a Stripe Checkout flow (`create-service-fee-checkout` Edge Function + `stripe-webhook`), tracked per passenger request and shown on MyRideScreen
- Forgot-password flow, including a GitHub Pages-hosted reset page
- A full app design/UI pass across auth, onboarding, home, my-ride, and admin screens
- A fare-split calculation utility (`src/services/fareSplit.ts`, proportional to distance) already exists and is wired into the admin's GroupDetailScreen, where an admin manually enters each passenger's distance and total fare to preview the split — this is an internal admin tool, not yet passenger-facing or tied to real payment collection

Today a passenger can sign up, log in, submit a ride request, get auto-matched into a group, and pay the fixed FLOQQ service fee in-app. Nothing yet exists for what happens between "group confirmed + fee paid" and "ride is over" — that gap is the roadmap below.

## Up next: the post-payment ride flow

Once the service fee is paid, six steps remain to take a group from "confirmed" to "done":

1. **Fare splitting by distance/time** — turn each passenger's share of the taxi fare into a real, passenger-facing calculation (not just the admin-only tool). `calculateFareSplit()` already does distance-proportional splitting; it needs a time-weighted option (or combined distance+time weighting) and needs to run automatically per group instead of via manual admin entry.
2. **Meeting point instructions** — tell each passenger in a group where and when to meet the others (and the taxi) after landing, based on their matched group and terminal/arrival data.
3. **In-ride live screen** — a screen during the ride showing distance-to-destination and estimated arrival for all 3 passengers in the group, i.e. live location/ETA sharing across the group.
4. **Taxi payment through the app** — let the group actually pay the taxi driver from within FLOQQ, rather than the current flat service-fee-only payment.
5. **Division of payments back to others** — settle up: whoever fronted the taxi payment gets reimbursed by the others according to their calculated share.
6. **Finalize the ride** — close out the group/request once payment and settlement are complete, so it moves out of "active" and into ride history.

## Open questions

- **Fare split**: distance only, time only, or a blend? Who enters the total taxi fare — the passenger who pays, or is it estimated upfront from Google Routes before the ride starts?
- **Meeting point**: fixed per-terminal pickup zones, or a point computed per group (e.g. centroid/first stop)? How is it delivered — push notification, in-app screen, both?
- **Live ETA screen**: does this need real-time location sharing between passengers' phones (new capability), or is it derived from the taxi's route progress? Needs a location-sharing/permissions design.
- **In-app taxi payment**: does FLOQQ take payment from the driver's side (driver has an app/terminal) or does one passenger pay the driver directly (cash/card) and get reimbursed via step 5? This determines whether step 4 needs a driver-facing surface at all. _(Open comment thread on the live doc — unresolved as of this snapshot.)_
- **Settlement (step 5)**: reuses the existing Stripe integration (service fee already uses Checkout + webhook) or needs a payout/transfer mechanism (e.g. Stripe Connect) to move money between passengers?
- **Finalize (step 6)**: what does "done" mean for a group/request in the data model — a new status value, a ride-history table? Any rating/feedback step expected here?
